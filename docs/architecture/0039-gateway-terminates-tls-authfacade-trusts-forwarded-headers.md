# 0039. The gateway terminates TLS; AuthFacade trusts its forwarded headers

- **Status:** Accepted
- **Date:** 2026-11-01

## Context

ADR 0020 named this gap outright: "TLS and proxy settings… the service still listens on plain HTTP, sends
no HSTS or security headers, and does not read forwarded headers. A deployment behind a proxy must add
them." ROADMAP.md's M1 lists it as required "before any shared environment." The practical cost of leaving
it open: `OpenIddictClientServiceCollectionExtensions` already sets `CookieSecurePolicy.SameAsRequest` for
both the session cookie and OpenIddict's own correlation cookie — the code was already written to make the
`Secure` flag correct the moment a real HTTPS request arrived, but nothing ever sent one. Every request in
the stack was plain HTTP, so `Request.IsHttps` was always `false`, and the `Secure` flag never set.

The gateway (ADR 0033) is the browser's one external origin for the dashboard, and already proxies
AuthFacade's own `/oidc/{**catch-all}` and `/callback` routes — but `LoginUi`'s actual "Log in with OpenEMR"
link bypassed it entirely, pointing straight at AuthFacade's own directly-published port
(`AuthFacade:BaseUrl` = `http://localhost:${AUTHFACADE_HTTP_PORT}`). That link, not the gateway, is what a
real user actually clicks first. Terminating TLS only at the gateway would have left the actual login entry
point unencrypted regardless.

## Decision

1. **The gateway terminates TLS with a self-signed dev certificate**, generated by
   `scripts/setup/new-dev-cert.sh` into `certs/` (git-ignored), the same kind of cert OpenEMR's own image
   already ships for `:9300`. Kestrel loads it via `Kestrel:Certificates:Default:Path`/`KeyPath`, set as
   Compose environment variables, with `certs/` mounted read-only. A new `GATEWAY_HTTPS_PORT` (default
   `7131`) is published alongside the existing plain-HTTP `GATEWAY_HTTP_PORT`.
2. **The plain-HTTP port now exists only to redirect.** `Program.cs` adds `UseHttpsRedirection()` before
   `MapReverseProxy()`. `HttpsRedirection:HttpsPort` is set to the *externally-published* port
   (`GATEWAY_HTTPS_PORT`), not Kestrel's own internal `8443` — the same internal/external split ADR 0012,
   ADR 0026 and ADR 0034 each already had to apply to a different address, now needed a fourth time for
   the redirect's own `Location` header.
3. **HSTS is a YARP response transform, not `UseHsts()` middleware.** This app does nothing but proxy —
   every request matches `MapReverseProxy()`, there is no other endpoint — so a header set by middleware
   never survives: the proxied response's own headers are what the client actually receives. Confirmed by
   testing: with only `UseHsts()` in the pipeline, `Strict-Transport-Security` never reached the client at
   all. `AddResponseHeader("Strict-Transport-Security", ..., ResponseCondition.Always)`, added to the same
   global transform as point 5 below, does reach it, on every route including WebApp's.
4. **`LoginUi`'s link now points at the gateway's HTTPS address**, not AuthFacade's own plain-HTTP port.
   `/oidc/login` is exactly the request the `Secure` cookie depends on reaching AuthFacade as HTTPS, and the
   gateway already had this route proxied; nothing but the configured base URL needed to change.
   AuthFacade's own port stays published and still plain HTTP — Scalar/OpenAPI access and the integration
   tests' direct `/health` check both still use it — it is simply no longer where the real login flow goes.
5. **The gateway sets `X-Forwarded-For` and `X-Forwarded-Proto` on every route it forwards**, via the same
   global transform HSTS uses (point 3), so it applies to WebApp's route too even though only AuthFacade
   reads either header. Action defaults to `Set`: the gateway always writes its own, real values, never
   appending to or trusting anything a client might have sent — there is nothing in flight for a caller to
   spoof here, only something for AuthFacade to decide whether to trust once it arrives.
6. **AuthFacade trusts those two headers, from one configured network only**
   (`ForwardedHeaders:TrustedNetworkCidr`, bound and validated like every other required setting in this
   project — `TrustedProxyOptions`). In Compose, that network is the stack's own, pinned to a fixed subnet
   (`DOCKER_NETWORK_CIDR`, default `172.28.0.0/16`) specifically so this can name it, instead of either
   hardcoding Compose's dynamically-assigned default subnet or trusting every caller. A request reaching
   AuthFacade's own directly-published port did not arrive from inside that network, so it cannot spoof
   either header no matter what it sends.
7. **The trust check is hand-rolled, not ASP.NET Core's own `UseForwardedHeaders`.** Built against the
   built-in middleware first; `ForwardedHeadersOptions.KnownIPNetworks` did not actually restrict anything
   against the installed 10.0.13 runtime in testing — a request from an address outside the configured
   network still had its `X-Forwarded-Proto` honored, confirmed in an isolated reproduction outside this
   codebase with `KnownProxies` cleared too, ruling out a leftover default. The one check this actually
   needs — is the immediate TCP peer inside the trusted network? — is small enough to write and verify
   directly (`ForwardedHeadersServiceCollectionExtensions.UseTrustedProxyForwardedHeaders`) rather than
   depend on library behavior that did not behave as its own option names imply.
8. **`X-Forwarded-Host` is not part of this.** The gateway already rewrites AuthFacade's routes' actual
   `Host` header (`RequestHeaderOriginalHost`, ADR 0034); a second, header-based mechanism for the same fact
   would be redundant.
9. **No code changes to the cookie configuration itself.** Both cookies already read
   `CookieSecurePolicy.SameAsRequest` — the `Secure` flag starting to actually appear is this decision taking
   effect against code that was already written to expect it.

## Consequences

- `Request.IsHttps` is `true` for any request that reached AuthFacade through the gateway, and both the
  `AuthFacadeSession` cookie and OpenIddict's own correlation cookie now carry `Secure` on that path.
  Verified against the real Compose stack as far as credentials outside this session allow: `/oidc/login`
  through the gateway's HTTPS port returns the correlation cookie with `Secure`; the same request against
  AuthFacade's own direct port correctly omits it; the registered `redirect_uri` OpenEMR receives is the
  gateway's HTTPS address, confirmed by `AuthFacadeStackTests` passing live. The full round trip including
  the session cookie is covered by `OpenIddictClientCallbackTests`/`ForwardedHeadersTests` against a fake
  OpenEMR server in-process; a real browser click-through with real OpenEMR credentials was not run in this
  session (no access to the stack's admin password) and is worth doing once before relying on this in a
  shared environment.
- A browser hitting the gateway's HTTPS port gets the same self-signed-certificate warning OpenEMR's own
  `:9300` already gives. Expected and already precedented in this stack (ADR 0020 already treats it as
  local-only).
- The per-address login rate limit (ADR 0038, a separate branch) gets a real side benefit once both merge:
  `X-Forwarded-For` means `Connection.RemoteIpAddress` reflects the actual browser's address instead of the
  gateway's, for any request that goes through it — closing the gap ADR 0018 already named ("behind a
  reverse proxy, every request looks like it came from the proxy").
- `scripts/stack/up.sh` and CI do not bring up `gateway`/`webapp`/`login-ui` at all today — a pre-existing
  gap from before this decision, not fixed here. The live verification for this change was done with a
  manually-run `docker compose up -d --build`.
- A production deployment terminating TLS somewhere else entirely (a cloud load balancer, a different
  reverse proxy) needs its own `ForwardedHeaders:TrustedNetworkCidr` and, if it is not Compose, its own
  equivalent of a fixed, known network to trust — this decision's defaults are this stack's own, not a
  general answer.

## Not covered

- **`LoginUi`'s own transport.** It still serves its static "Log in with OpenEMR" page over plain HTTP; only
  the link's destination changed. The page itself carries no credentials (ADR 0026 point 10), but an
  on-path attacker could still rewrite the link itself before the browser ever follows it. A smaller,
  separate gap than the one this decision closes.
- **`scripts/stack/up.sh` and CI not starting the gateway stack.** Pre-existing, unrelated to TLS.
- **A load-balancer-in-front-of-the-gateway topology.** `ForwardLimit`-equivalent reasoning for a second hop
  is not addressed; today's trust check assumes exactly one hop (the gateway itself).

## Alternatives considered

- **Terminate TLS inside AuthFacade itself, not the gateway.** Rejected: the gateway is already the one
  external origin a browser talks to (ADR 0033); terminating TLS a second time, deeper in, would duplicate
  the cert/port/redirect machinery for no benefit over doing it once at the edge.
- **Leave `LoginUi` pointed at AuthFacade's own port.** Rejected: it is the actual link a real user clicks,
  and leaving it unencrypted would mean this decision protected a path nobody takes while leaving the real
  one open.
- **Trust Docker's own dynamically-assigned default subnet instead of pinning one.** Rejected: it is not a
  fixed, known value to check against, and would either need discovering it at runtime or trusting whatever
  it happens to be — a pinned subnet is one line and removes the question entirely.
- **Debug or report the `ForwardedHeadersOptions.KnownIPNetworks` discrepancy upstream before shipping a
  workaround.** Not pursued for this change: no network access to file or search an issue from this
  environment, and the replacement is small enough to verify on its own merits regardless of the library's
  root cause.

## Related decisions

Closes the gap ADR 0020 named in its own "Not covered" section. Builds on ADR 0033's gateway and reuses the
internal/external address split ADR 0012, ADR 0026 and ADR 0034 each already established. Makes the
`CookieSecurePolicy.SameAsRequest` choices in `OpenIddictClientServiceCollectionExtensions` (ADR 0024, ADR
0026) take effect for the first time. Gives ADR 0038's per-address rate limit the real client address once
both are merged.
