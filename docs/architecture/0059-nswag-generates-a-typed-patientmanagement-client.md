# 0059. NSwag generates a typed PatientManagement client from a committed OpenAPI snapshot

- **Status:** Accepted
- **Date:** 2026-11-15
- **Builds on:** [0031](0031-nswag-client-generated-from-a-committed-snapshot.md), [0058](0058-patientmanagement-openapi-declares-the-gateway-secret-and-reflects-validation-attributes.md)

## Context

ADR 0031 built exactly this for AuthFacade: an NSwag-generated C# client in its own project, from a
committed OpenAPI snapshot regenerated by a dev script that runs the real API briefly with placeholder
config. PatientManagement's own OpenAPI document was only just made actually correct (ADR 0058 --
the gateway-secret scheme and DataAnnotations constraints now show up in it); generating a typed client
from it now reuses a pattern this repo already proved out, rather than inventing a second approach.

The one real difference from AuthFacade's script: PatientManagement.Api has no `/health` endpoint to
poll for readiness, so the generation script polls `/openapi/v1.json` itself instead -- a more direct
check anyway, since that's the actual thing being waited on.

## Decision

1. **`OpenEmrNext.PatientManagement.Client`**, a new class library, holds the generated client --
   same shape as `OpenEmrNext.AuthFacade.Client`: no `ProjectReference` to the Api project, an
   `OpenApiReference` pointing at a committed file (`OpenAPIs/PatientManagement.json`) with
   `CodeGenerator="NSwagCSharp"`, `/GenerateClientInterfaces:true /JsonLibrary:SystemTextJson
   /UseBaseUrl:false` (callers supply their own `HttpClient.BaseAddress`).
2. **`scripts/dev/generate-patientmanagement-openapi.sh`** regenerates the snapshot: builds the Api,
   runs it on a random loopback port with placeholder values for `PatientManagementDb:*`,
   `AdvanceDirectiveStorage:RepositoryRoot`, and `InternalGateway:Secret` (all `[Required]` +
   `ValidateOnStart()`, none ever committed), polls `/openapi/v1.json` directly for readiness (no
   `/health` endpoint exists here), reads the document, strips `servers` (would just be this run's
   random port), writes it, stops the process.
3. **The database is never actually touched.** EF Core's connection is lazy -- registering
   `PatientManagementDbContext` doesn't connect, and generating the OpenAPI document never queries a
   repository -- so the placeholder `PatientManagementDb:*` values never need to resolve to anything
   real, unlike AuthFacade's script, which does need a reachable (if minimal) OpenEMR instance for its
   own readiness probe.
4. **Added to `OpenEMR-Next.slnx`** under the existing `/src/Services/PatientManagement/` folder.

## Consequences

- A typed, interface-based client (`IPatientManagementClient`) now exists for every endpoint --
  registration, insurance, advance directives, and the FHIR Patient API -- the same way
  `IAuthFacadeClient` already does for AuthFacade. Nothing in this repo consumes it yet; that's a
  separate, later decision (a future WebApp/BFF caller, or a test project).
- The FHIR endpoints' generated methods return `object` for their response bodies
  (`FhirGetPatientAsync`, `FhirSearchPatientsAsync`, etc.), not a typed `Hl7.Fhir.Model.Patient`/
  `Bundle`/`OperationOutcome`: the OpenAPI document's own schema for these (inherited from how
  `FhirPatientEndpoints` declares `Produces<T>` against Firely SDK types) doesn't carry a shape NSwag
  can generate a concrete model from. This is a property of the document those endpoints already
  produced before this ADR, not something client generation introduces; a caller needing a typed FHIR
  response would deserialize the `object` (really a `JsonElement`) itself, the same way any OpenAPI-
  driven FHIR client would need to given FHIR resources' deliberately polymorphic shape.
- Regenerating the snapshot after any Api change to request/response shapes, validation attributes, or
  the security scheme requires re-running the script and reviewing the diff -- the same manual step
  AuthFacade's own client already requires, not automated by this ADR.

## Alternatives considered

- **Generate the client from a build-time live document** (`Microsoft.Extensions.ApiDescription.Server`).
  Rejected for the same reason ADR 0031 already rejected it for AuthFacade: it runs the app's real
  startup validation with no server listening, which fails the same way a bare `dotnet run` would
  outside Docker, now that `InternalGatewayOptions.Secret` is one more required setting never
  committed to a file.
- **Kiota or a hand-written client.** Not reconsidered: ADR 0031 already weighed NSwag against Kiota
  for AuthFacade and chose NSwag; nothing about PatientManagement's document shape (plain JSON bodies,
  no form-urlencoded quirks) gives a reason to pick differently for a second service.
