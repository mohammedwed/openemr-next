# 0060. PatientManagement is deployed and reachable through the Gateway; WebApp gets a first frontend slice

- **Status:** Accepted
- **Date:** 2026-11-15
- **Builds on:** [0030](0030-bff-proxy-forwards-to-the-gateway-not-each-service.md), [0033](0033-gateway-fronts-webapp-and-authfacade.md), [0048](0048-authfacade-stays-the-bridge-gateway-validation-deferred.md), [0055](0055-patientmanagement-api-gated-by-a-shared-secret-identity-forwarding-deferred.md), [0059](0059-nswag-generates-a-typed-patientmanagement-client.md)

## Context

`MainLayout.razor` had a disabled "Patients" nav link waiting for this. ROADMAP.md's M3 milestone
named "routes to the new services (Patient Management, Clinical Care)" as remaining work, explicitly
"blocked on M4/M5 existing" -- M4 now exists, so that trigger has fired. Building a frontend slice on
top of it meant standing up the whole path first: PatientManagement had no Dockerfile, no
docker-compose service, and no Gateway route at all.

## Decision

1. **`src/Services/PatientManagement/Dockerfile`** -- mirrors AuthFacade's own multi-stage build.
   **Found along the way**: the repo-root `.dockerignore` only applies to builds whose Compose context
   is the repository root (currently just WebApp); a per-service build (context scoped to its own
   directory, like this one and AuthFacade's) needs its own `.dockerignore`, which PatientManagement
   never had. Without it, `COPY . ./` copied every project's local `obj/`/`bin/` folders (generated by
   `dotnet build` on the host) over the container's own freshly-restored ones, whose NuGet asset files
   point at `/root/.nuget/packages` -- the host's folders point elsewhere, so the container's copies
   got silently overwritten with ones referencing packages that don't exist inside it. Confirmed by
   direct inspection: `dotnet restore` genuinely installed `Microsoft.AspNetCore.OpenApi` into
   `/root/.nuget/packages`, and `project.assets.json` correctly listed it, but `dotnet publish
   --no-restore` still failed with `NETSDK1064` until a `src/Services/PatientManagement/.dockerignore`
   (identical to AuthFacade's own) was added.
2. **`docker-compose.yml`**: new `patient-management` service, no published host port (only the
   Gateway may reach it, per ADR 0055), depending on `mysql` and `seed-patient-management-db`. Mounts
   the same `sitesvolume` OpenEMR itself writes to, at `/sites`, so
   `AdvanceDirectiveStorage__RepositoryRoot` (`/sites/default/documents`) resolves to the real shared
   path. A new `INTERNAL_GATEWAY_SECRET` (`.env.example`, `scripts/setup/new-env.sh`, CI's own `.env`
   step) is shared between this service and the `gateway` service only.
3. **`src/Services/Gateway/OpenEmrNext.Gateway/Program.cs`**: a new `patientmanagement` cluster and two
   routes, `/api/v1/patients/{**catch-all}` and `/fhir/{**catch-all}` (narrowed to `/fhir/Patient/{**catch-all}` by ADR 0079, when Clinical Care began to serve the clinical FHIR resources) -- more specific than AuthFacade's
   existing `/api/{**catch-all}`, so the same route-precedence reasoning already documented there
   applies. A request transform, scoped to only this cluster (checked via
   `TransformBuilderContext.Cluster.ClusterId`, not applied globally like the `XForwardedFor`/HSTS
   transforms), attaches `X-Internal-Gateway-Secret` unconditionally -- the one thing ADR 0055 already
   scoped to "whichever caller eventually routes through the gateway," not a new per-user authorization
   decision. Verified against the real stack, not just reasoning about the YARP config: brought up
   `docker compose` with `patient-management` included, and two new `GatewayStackTests` theory cases
   (`/api/v1/patients`, `/fhir/Patient`) prove a caller presenting no secret of its own still gets a
   real 200 from PatientManagement, not WebApp's SPA fallback.
4. **A new `GET /api/v1/patients` endpoint** (`PatientEndpoints.cs`), returning a small
   `PatientSummaryResponse` list. No new Domain or persistence work: it reuses
   `SearchPatientFhirRecordsUseCase`/`IPatientFhirRepository.SearchAsync` (`PatientFhirView`, already a
   plain read-model, not a FHIR type) -- the existing `GET /fhir/Patient` search's own machinery,
   projected to a shape simpler than a FHIR Bundle. The alternative -- parsing a FHIR `Bundle` in the
   browser -- was rejected because NSwag can't generate a typed model for it (Firely SDK types have no
   OpenAPI schema NSwag can read; the generated client's FHIR methods already return bare `object`).
5. **`OpenEmrNext.WebApp`** gets `IPatientManagementClient` registered alongside `IAuthFacadeClient`
   (`Program.cs`), each with its own `HttpClient` and its own circuit-breaker instance -- so one
   dependency's outage never trips the other's breaker. `AuthFacadeCircuitBreakingHandler` is renamed
   `TransientFailureCircuitBreakingHandler`: the class had no AuthFacade-specific logic, and is now
   genuinely reused for two independent dependencies. Two new pages, `Pages/Patients/Index.razor` (a
   list) and `Pages/Patients/Register.razor` (a form), both gate on `IAuthFacadeClient.GetCurrentUserAsync()`
   the same way `Home.razor` already does -- PatientManagement's own gate (ADR 0055) only checks that a
   call came through the gateway, not which user is behind it, so the page itself is what actually
   keeps a signed-out visitor from registering or viewing patients, not the backend. `RegisteredBy` uses
   a fixed placeholder id (`PlaceholderRegisteredById = 1`), the same framing ADR 0055 already gave this
   gap -- not a new decision.
6. **A real namespace collision, found and fixed while wiring both generated clients into one app**:
   `OpenEmrNext.AuthFacade.Client` and `OpenEmrNext.PatientManagement.Client` each generate their own
   `ApiException` class. A page that calls both (as both new Patient pages do, via
   `IAuthFacadeClient.GetCurrentUserAsync()` for the sign-in check) needs both namespaces in scope,
   which makes the bare name ambiguous. Resolved with two explicit `@using X = Namespace.ApiException`
   aliases per page -- the same disambiguation shape this codebase already used for the
   `Patient`/`FhirPatient` collision in `FhirPatientEndpoints.cs`, not a new pattern invented here.

## Consequences

- ROADMAP M3's "routes to the new services... blocked on M4/M5 existing" item is partially closed for
  Patient Management specifically (Clinical Care's own route, when that service exists, is unaffected
  by this ADR).
- PatientManagement is now a real, running container in the Compose stack and in CI
  (`.github/workflows/ci.yml`'s `docker compose up` service list), not just source code with no
  deployment path.
- Verified end to end against the real running stack, not just unit/integration tests in isolation: a
  `curl` through the gateway (no secret presented by the caller) successfully registered a patient and
  then listed it back -- the same round trip the WebApp pages drive through the generated client.
- `AuthFacade__BaseUrl`/`WebApp__BaseUrl`-style Gateway configuration gains two more required values
  (`PatientManagement__BaseUrl`, `InternalGateway__Secret`); a future third backend service repeats
  this same shape, not a new one.
- The identity-forwarding gap ADR 0055 named is now visible in the UI too (a placeholder id), not just
  in the Api's own request bodies -- still the same open, tracked gap, not widened or narrowed by this
  change.

## Alternatives considered

- **List patients via the FHIR search endpoint directly in the browser.** Rejected: no typed model
  NSwag can generate from it; parsing a raw FHIR `Bundle`'s JSON by hand in a Blazor page for a plain
  list view is the wrong trade when the same search already has a non-FHIR read-model to project from
  instead.
- **A direct AuthFacade BFF-proxy cluster to PatientManagement**, bypassing the Gateway. Rejected:
  ADR 0030 already settled this -- new backend services are reached through the Gateway, which is also
  the only place that should ever hold `InternalGateway:Secret`.
- **Share one `HttpClient`/circuit breaker between both generated clients in WebApp.** Rejected: a
  PatientManagement outage would then also trip AuthFacade's breaker (and vice versa), which is a
  correctness regression, not a simplification -- these are independent dependencies.

## Related decisions

Closes the Patient Management half of ROADMAP M3's remaining routing item. Makes
[0055](0055-patientmanagement-api-gated-by-a-shared-secret-identity-forwarding-deferred.md)'s gate
actually reachable from somewhere real, and gives [0059](0059-nswag-generates-a-typed-patientmanagement-client.md)'s
generated client its first consumer.
