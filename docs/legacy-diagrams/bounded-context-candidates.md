# Candidate bounded contexts

This is a pragmatic grouping of the existing `interface/`, `library/`, and
`src/` code. It is not a proposed package reorganization and is not an
exhaustive file inventory. Each row shows 10–15 representative files or
folders, selected to expose the likely responsibilities, classes, tables, and
request entry points.

Table names are based on SQL visible in the cited files. Where a table or
route could not be established from the inspected source, it is marked
**not found** rather than inferred.

## Boundary observations

1. The strongest current boundaries are directory and API-route boundaries,
   not consistently enforced domain boundaries. For example, patient,
   encounter, medication, document, and message resources appear in the
   standard API route file [`apis/routes/_rest_routes_standard.inc.php`](../apis/routes/_rest_routes_standard.inc.php).
2. The legacy UI is cross-context by construction because feature pages include
   [`interface/globals.php`](../interface/globals.php), which includes the
   database and authentication bootstrap.
3. `src/` has clearer candidate context folders—`Billing`, `Patient`, `Rx`,
   `Pharmacy`, `ClinicalDecisionRules`, `RestControllers`, and `Services`—but
   some modern services still use the legacy SQL wrappers.
4. Tables such as `patient_data`, `users`, `forms`, `form_encounter`, `lists`,
   and `list_options` are shared data hubs. They should be treated as
   integration points or ownership candidates, not assumed to belong to only
   one context.
